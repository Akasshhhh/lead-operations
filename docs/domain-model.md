# Domain and Database Model

## Persistence stack

- PostgreSQL 16 is the durable source of truth.
- SQLAlchemy 2.x async models use `asyncpg`.
- Alembic owns migration history.
- UUID identifiers are generated by the application.
- JSONB is limited to bounded metadata, event payloads, scenario definitions,
  structured answer values, and evaluation values.

## Logical schemas

### `lead`

```text
leads
qualification_profiles
qualification_answers
lead_scores
lead_score_history
```

The lead schema owns lead identity, current qualification, and deterministic
score history. Qualification answers are unique per profile and field key.

### `conversation`

```text
conversations
calls
messages
transcript_segments
conversation_summaries
```

Conversation and transcript records are append-oriented where practical.
Message and transcript sequence numbers are unique per conversation.

### `workflow`

```text
followups
followup_attempts
handoffs
```

Follow-ups have durable idempotency keys. Attempts are unique per follow-up and
attempt number.

### `evaluation`

```text
scenarios
evaluation_runs
evaluation_results
```

Evaluation scenarios and results are independent of production lead mutations.

### `platform`

```text
processed_events
domain_events
provider_health
fault_injections
audit_log
```

The platform schema contains the transactional event outbox, consumer
idempotency records, provider health snapshots, development fault controls,
and administrative audit records.

Module 5 adds `ix_domain_events_unpublished`, a partial index on
`(occurred_at, event_id)` where `published_at IS NULL`, in migration
`6b30f517c820`. The relay uses existing publication-attempt/deadline fields;
consumer database effects and the `(event_id, consumer_group)` processed marker
commit in one transaction. No business table fields were changed.

## Migration workflow

```bash
DATABASE_URL='postgresql+asyncpg://voice_ai:voice_ai_dev_password@localhost:5432/voice_ai' \
  .venv/bin/alembic upgrade head
```

Migrations create logical schemas before tables and remove them only after all
tables have been downgraded. Migration tests verify upgrade, downgrade, and
upgrade-from-empty behavior against PostgreSQL.
